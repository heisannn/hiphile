# UI を AntiWebUI に移す

2026-11-12 に計画した。デスクトップアプリを GPUI と GPUI Kit から
[AntiWebUI](https://github.com/bea4dev/AntiWebUI) に移し、画面を `anti-webui-md3e` で Material 3
Expressive にデザインし直してみる。どんな感じになるかを見るための試しで、リリースや切り替えは決めていない
（[リリースするなら](#リリースするなら)）。まずは AntiWebUI をフォークせず、上流のものをそのまま使って
できる範囲を作る。足りないものは Hiphile の側でしのぐか、制限として残す（[フォークするなら](#フォークするなら)）。
ウィンドウはメインの 1 つだけにし、設定はその中のポップアップとして作り直し、ミニプレーヤーは後回しにする。
コアは [Extracting the core](../core/extraction.md) が残した形のままで、ビューはコアのハンドルに従い、
ビューの状態だけを持つ。例外はカバーの口の追加だけ（[カバー](#カバー)）。[決まったこと](#決まったこと)は
同じ日に決めた。

| | |
| --- | --- |
| 目標 | 素の AntiWebUI と `anti-webui-md3e` で Material 3 Expressive にデザインし直したアプリを GPUI 版の横に作り、比べて、続けるか、フォークするかを決める |
| 規模 | gpui-kit に依存するクレートは 14 個。ビューは約 17,100 行、そのテストは約 8,500 行（`#[gpui_kit::test]` が 260 個）。コアのクレートのテスト 378 個が `gpui-host` を通して GPUI の executor で動いている |
| 対応する環境 | macOS 14 以降だけ（arm64 と x64） |
| AntiWebUI の使い方 | 上流のリポジトリをリビジョン固定の git 依存で使う。フォークしない |
| ウィンドウ | メインの 1 つだけ。設定は同じウィンドウのポップアップにし、ミニプレーヤーは後回し |
| 大きな不足 | メニューバー、アプリから取れるウィンドウハンドル、ウィンドウの位置・最前面・最小サイズ、キーバインド、テキストの省略記号が無い。仮想リストの行の高さは 1 種類だけ |
| 大きなリスク | AntiWebUI は 10 日目（最初のコミットは 2026-11-02、70 コミット、作者は主に 1 人、CI なし）。足りないものの多くを、AntiWebUI が持つ AppKit のウィンドウとメニューを外から触ってしのぐ |
| 順序 | 検証、テスト用 executor、土台、プレーヤー、各画面、歌詞と設定、比較（[手順](#手順)） |
| GPUI 版と並べて作る | 新しいアプリは `next/` で作り、リリースには入れない。GPUI 版は今までどおり。2 つは 1 つのウィンドウもイベントループも共有できない |

## 調べた時点の AntiWebUI

`25e82a1`（2026-11-11）を読んだ。この節のパスは AntiWebUI のリポジトリからの相対パスで、`dNN` は
その `docs/design/NN-*.md` を指す。

### 合うところ

- **コアの形。** AntiWebUI のシグナルはスレッドローカルで細粒度に更新される。コンポーネントの関数は
  一度だけ走り、クロージャは読んだシグナルが変わったときに走り直す（d02）。コアはすでにスナップショットを
  `watch` に、通知を `broadcast` に出している（コアのルール 3）ので、ビューはそれぞれをシグナルに
  変えればよく、コアがどう動いているかを知らなくてよい。
- **UI スレッドへの受け渡し。** `ui_channel(f) -> UiSender<T>`（`anti-webui-core/src/channel.rs:94`）は
  `Send` な送り口を返す。送るとループが起き、`f` が UI スレッドで batch の中で走る。
- **終了。** `App::run` は最初のウィンドウが閉じると戻り、⌘Q や Dock の「終了」はそのウィンドウへの
  閉じる要求になる（`anti-webui-macos/src/app.rs:30-37`）。`main` は `run` が戻ったあとメインスレッドで
  `Hiphile::shutdown()` を呼べばよく、フックは要らない。
- **ダイアログ。** md3e のダイアログは widgets の `modal_with` の上にあり、同じウィンドウの中の `portal` に
  描かれる（`anti-webui-widgets/src/dialog.rs:159-179`）。Tab が中に留まり、Escape と scrim で閉じる。
  メニューやツールチップのポップアップは、macOS では枠の無い子ウィンドウになる
  （`anti-webui-macos/src/popup.rs:1-2`）。
- **画像。** `img` はファイルのパスかバイト列を受け取り、描く大きさでワーカースレッドがデコードし、
  デコード済みの絵をスレッドごとに 256 MB まで持つ（d22）。キャッシュのキーはパスか、`Arc` のアドレス。
- **長いリスト。** `virtual_list` は見えている行だけを作る。10 万行の表のスクロールは 1 フレームの中央値が
  0.16 ms（d21:139）。行が使い回されてもドラッグは続く（d23:89）。
- **md3e。** 形が変わるボタン、ボタングループ、アイコンのトグル、FAB、ナビゲーションレール、タブ、トップ
  アプリバー、検索、サブメニューのあるメニュー、ダイアログ、シート、スナックバー、ツールチップ、スライダー
  （通常、中央、範囲、波線）、プログレス（線、円、波線）とローディングインジケーター、パスワードの使える
  テキストフィールド、チップ、カード、カルーセル、リスト、34 の表現的な形、軸をアニメーションできる
  Material Symbols、モーションのトークンがある。配色は実行時に種の色からすべてのスキームバリアントで作れ、
  `dynamic::seed_colors` は画像のピクセルから種の色を見つける。つまり再生中の曲のカバーに配色を合わせ、
  `set_color_scheme_animated` でクロスフェードできる。部品の振る舞いと見た目は分かれていて、標準の部品の
  振る舞いに自分の見た目を載せられる（`slider_with` などの `*_with`、d33）。
- **テスト。** `core::Ui` はウィンドウなしで合成イベントとフレームを受け取り、
  `accessibility::snapshot()` は役割と名前でノードを探す。ここまでは GPU が要らない。`app::headless` は
  PNG を描き、こちらは GPU のアダプタが要る。
- **依存関係。** このワークスペースに試しのクレートを作り、`anti-webui`（macOS、Windows、SVG）、
  `anti-webui-md3e`、`desktop` を有効にした `hiphile-core` をリンクした。ロックは 33 パッケージ増えた
  だけで、既存のバージョンは変わらなかった。wgpu は crates.io のもので、上流の `[patch.crates-io]` の
  フォークは要らなかった。そのフォークの `adapter_filter` を使うのは `cfg(windows)` だけ
  （`anti-webui-wgpu/src/lib.rs:129-131`）。このマシンの温まったキャッシュで 25 秒でビルドできた
  （まっさらなビルドは測っていない）。

### 足りないところ

「素のままでの手」の `next-platform` は、objc2 で AppKit を直接呼ぶ Hiphile のクレート
（[クレート](#クレート)）。AntiWebUI が作った `NSWindow` は、メインスレッドで `NSApp` のウィンドウの一覧から
タイトルで探す。

### ここでビルドして分かったこと

- **小数のリテラルが CI で落ちる。** スタイルの setter は `impl Into<f32>` を受け取る
  （`anti-webui-style/src/styled.rs:3-15`、`:124`）。そのため `.p(16.0)` のリテラルの型が決まらず、
  将来非互換の lint `float_literal_f32_fallback` のもとで `f32` に落ちる。CI と同じ
  `cargo clippy -- -D warnings` では、試しのクレートの `.p(16.0)` 1 つがエラーになった。Hiphile では
  `16.0_f32` と書く。AntiWebUI 自身の widgets と md3e でもこの lint が 287 回出た。今は cargo が git
  依存の lint を抑えるので問題にならないが、この lint がハードエラーになると、上流が setter を変えるまで
  AntiWebUI がビルドできなくなる。
- **macOS で 1 つのスレッドにウィンドウが 2 つあるとスタックがあふれうる。** macOS の `Session` には
  `request_redraw(key)` と `redraw_pending(key)` が無い。そのため runner のトレイトのメソッドが自分自身を
  呼ぶ（`anti-webui-app/src/runner.rs:688-693`、rustc の `unconditional_recursion`）。`redraw_changed`
  （`:867-876`）は、スレッドにウィンドウが 2 つあるか root（Wayland のシェル用の隠し API、
  `anti-webui-core/src/window.rs:709-720`）があるとそこに届く。普通のアプリは root を作らないので、
  ウィンドウがメインの 1 つだけなら届かない。読んだだけで実行はしていない。ミニプレーヤーを戻すときに
  確かめる。

## 構成

### クレート

新しいクレートは `next/`（`members` の 2 つ目のグロブ）に置き、パッケージ名が重ならないよう `next-` を
付ける。`release-plz.toml` では `hiphile-cli` と同じく `release = false` にし、`changelog_include` にも
入れない。release-plz はどのクレートの変更でも共有のバージョンを上げるので、こうしないと `next-*` の
変更が中身の変わらない GPUI 版のリリースを起こす。

| クレート | 置き換えるもの | 持つもの |
| --- | --- | --- |
| `next-host` | `gpui-host`、`ui` の HTTP クライアントとカバーのキャッシュ | アプリの tokio ランタイムとその上の `Spawner`。`follow`、`notices`、`on_ui`。カバーの取得と共有。テストで落ち着くまで回す道具 |
| `next-platform` | GPUI の `set_menus` と、GPUI がしていたウィンドウの扱い | AppKit を直接呼ぶもの：メニューバー、メインウィンドウの枠・最小サイズ・前に出すこと・信号機ボタン、外観、動きを減らす設定、`LANG`。メインスレッドでだけ呼ぶ。`unsafe_code` はこのクレートのモジュールでだけ許し、それぞれに理由を書く。デスクトップ専用で、`hiphile-core` の下には入れない |
| `next-ui` | `ui`、`actions` のメニューとグローバル | テーマとトークン、キーマップ、フォーカスを戻す仕組み、画面をまたぐコマンド、共通の部品 |
| `next-account`、`next-home`、`next-library`、`next-artists`、`next-songs`、`next-playlists`、`next-favorites`、`next-search`、`next-player`、`next-settings` | 同じ名前のクレート | 1 つの画面、パネル、ポップアップずつ。テストは `<view>/tests.rs` |
| `next-hiphile`（バイナリ `hiphile-next`） | `hiphile` | 起動、シェル、ルーティング、メニューバーのコマンド |

`actions` の struct のアクション（`ShowAlbum`、`AddToPlaylist`、`PlaySongs` など）は `Command` の enum に
なり、シェルが処理し、画面は渡されたハンドルを通して送る。3 つのグローバル（`PlaylistChoices`、
`KnownFavorites`、`SkipInstrumentals`）はもともとコアのスナップショットの写しなので、シェルが一度だけ
従うシグナルになる。

### スレッドと状態

- コアは `main` が作るマルチスレッドの tokio ランタイムで動き、`Executor::tokio` として渡される
  （`hiphile-cli` は current-thread のランタイムを使っている）。`net` は自分のランタイムを持ち続ける。
  `run` が戻ったら `Hiphile::shutdown()`、ランタイムの `shutdown_timeout`、最後の `net::Client` の順に
  落とす（コアのルール 11）。`shutdown_timeout` にするのは、ライブラリの同期がブロッキングのスレッドで
  `block_on` していて、ランタイムを普通に落とすとその終わりを待つため。
- ビューは `next-host` を通して `watch` をシグナルに変える。スナップショットそのものは送らず、「変わった」
  とだけ送り、UI スレッドで最新の値を読む。これで続けて出た変更は最後の 1 つにまとまり、古い値に戻る
  こともなく、UI が止まっている間にキューが伸びることもない。まだ届いていない知らせがあるときは送らない。
  スケッチ（その印は省いた）：

  ```rust
  pub fn follow<T: Clone + Send + Sync + 'static>(
      executor: &Executor,
      mut changes: watch::Receiver<T>,
  ) -> Signal<T> {
      let latest = changes.clone();
      let value = signal(changes.borrow_and_update().clone());
      let to_ui = ui_channel(move |()| value.set(latest.borrow().clone()));
      let task = executor.spawn(async move {
          while changes.changed().await.is_ok() {
              to_ui.send(());
          }
      });
      on_cleanup(move || drop(task));
      value
  }
  ```

- オーナーの外で呼ぶと、`on_cleanup` は渡されたクロージャをその場で捨てる（`reactive.rs:382-394`）ので、
  タスクがすぐ止まって黙って更新されなくなる。`follow`、`notices`、`on_ui` はオーナーが無ければ
  デバッグビルドで panic する。
- `notices` は `broadcast` に対して同じ形で、`Lagged` は飛ばす。チャンネルどうしの順序は送った順では
  なく登録した順になる（`channel.rs:111-121`）。そのため、通知のハンドラで状態が要るときは、
  `follow` のシグナルではなくコアの `snapshot()` を読む。
- `on_ui(task, f)` はコアの `executor::Task<R>` を待ち、オーナーが残っていれば `f` を UI スレッドで
  走らせる。チャンネルはオーナーごとに 1 本にし、待っているものの表を持たせ、取り消しのハンドルを返す。
  1 回ごとにチャンネルを作ると、受け口がオーナーの寿命まで残って増え続ける。
- これらが `observe`、`observe_in`、`subscribe`、`subscribe_in`、`notify_on_change`（合わせて 43 か所）を
  置き換える。呼び出しの結果をすぐ見せるビューは、今と同じく呼んだ直後に `snapshot()` を読む。
- シグナルはスレッドをまたがない。`Signal<T>` は ID だけなので `Send` になってしまうが、ランタイムの無い
  スレッドで使うとパニックし、別の UI スレッドでは同じ ID が別の値を指しうる。UI スレッドの外のコードは
  シグナルではなく `UiSender` を持つ。
- 再生位置は出されない（コアの抽出の step 7 で決めた）。プレーヤーバーは 250 ms ごと、歌詞は 50 ms ごとに
  `position()` を読む。今と同じで、見えている間 `set_timeout` をかけ直す。一定間隔のタイマーは無い。

### カバー

`CoverStore` のパスは非公開で、`get` はバイト列を返す（`crates/catalog/src/covers.rs:77-111`）。コアの
`cover_image` も `Arc<[u8]>` を返す（`crates/hiphile-core/src/covers.rs:8-17`）。`get` は LRU の更新、
空のファイルの修復、鮮度の判定もするので、パスを外から組み立てて読むとこれらを通らない。

- コアに、なければ取得し、LRU を更新して、ファイルのパスを返す口を足す（例：
  `cover_file(request) -> Task<Option<PathBuf>>`）。キャッシュの無い構成（`Caches::None`）では
  バイト列を返し、同じカバーには同じ `Arc<[u8]>` を渡して、`img` のキャッシュが効くようにする。
- `next-host` のカバーは、取得、同じカバーを使う行どうしでの共有、どの行も要らなくなったときの取り消し、
  読み込み中の表示を受け持つ。

### キーとメニュー

- 今のキーマップは仮なので移さず、新しく決める。仕組みだけをここで決める。
- キーの経路は 2 つに分ける。
  - **メニューバーにあるキー**は、アプリ全体のコマンドとしてメニューが受ける。AppKit はこれらのキーを
    ビューより先に取る（d38:158）。コマンドが使えないとき（ダイアログが開いているときなど）は項目を
    無効にし、キーも効かなくする。
  - **それ以外のキー**は `next-ui` のキーマップが受ける。キーマップはバインドを
    `(キーストローク, コマンド, コンテキスト)` で持ち、macOS では ⌘ を使う（`Modifiers::primary`）。
    コンテキストは `key_context(name)` を付けた要素で、そのハンドラはそのコンテキストのバインドのうち、
    そこで有効なコマンドのものを使う。こうして GPUI と同じく内側のコンテキストが勝つ。
- キーマップの細部：
  - 使ったキーには `stop_propagation` と `prevent_default` の両方をかけ、部品の既定の処理を止める。
  - フォーカスがテキストの入力欄にあるときは、文字になるキーを入力欄に譲る。
  - フォーカスが無いとキーはルートにしか来ないので、フォーカスを失ったときに戻す仕組みを `next-ui` が
    持つ。
- コマンドの有効・無効は memo で決まる。シェルは今と同じく、使えるときだけコマンドを登録する
  （`app_shell.rs:1231-1355`）。メニューバーは同じ memo を読んで項目を有効にし、チェックを付け、`effect` で
  作り直す。ツールチップとメニューにはキーストロークを出す。
- メニューバー（`next-platform`）は今と同じ 4 つ：hiphile、Library、View、Controls。項目は `Command` を
  `UiSender` で送るので、AppKit のコールバックの中でリアクティブなコードは走らない。

### ウィンドウ

ウィンドウはメインの 1 つだけで、`App::run` でメインスレッドに開く。

- 保存した位置と大きさで開く（新しく足す）。最小 900×560。閉じると終了する。タイトルバーの帯は無く、
  信号機ボタンはレールの上端に重なる（[画面の各部](#画面の各部)）。位置と最小サイズは `next-platform` が
  `NSWindow` に設定する。
- 設定は同じウィンドウのポップアップ（[画面の各部](#画面の各部)）。メニューの「Settings…」とそのキーで開き、
  Escape と scrim で閉じる。シグナルも配色もメインの画面と同じものを使い、変えた外観は後ろの画面にも
  すぐ出る。
- ミニプレーヤーは後回し。戻すときは `spawn_window` で専用のスレッドに開く（1 つのスレッドの 2 つの
  ウィンドウは macOS で再帰しうる）。そのウィンドウはシグナルを共有しないので、プレーヤーのハンドルに
  直接従い、フォント、配色、画像のキャッシュを自分のスレッドで用意する。フォーカスを取らないウィンドウは
  素のままでは作れない。

### テスト

- `gpui_host::executor(cx)` で動くコアのテスト 378 個は、先に `executor` の決定的な executor へ移す。
  その executor は次のものを持つ：
  - シングルスレッドで、`run_until_parked`、`advance_clock`、`tick` を持つ。
  - 本物のネットワークのスレッドを待つための `allow_parking` を持つ。コアのテストで 43 か所使っている。
  - ブロックする仕事はその場で走らせる（GPUI と同じ）。
  - `spawn` が戻る前に仕事を poll しない（コアのルール 4）。
  - 落とすと取り消す。

  `TestAppContext` と `cx.update` を使っているところは書き換えになるが、テストの筋は変えずに済む。
- ビューのテストは、`hiphile_core::test_support` の偽のサーバーを使ってビューを `core::Ui` に載せ、合成
  イベントを送り、`accessibility::snapshot()` でノードを探す。コアは決定的な executor で動かす。
  `next-host` のテスト用の道具が、executor を park するまで回し、`ui_channel` を流し、フレームを進める
  ことを、何も起きなくなるまで繰り返す。22 個の `debug_selector` は名前か役割になる。タイマーやばねは
  進められないので、時間ではなく状態を確かめる。
- テストのコアはメディアコントロールにつながない。ハンドル無しでつなげるようにしたあとも、テストが
  実機の Now Playing に届かないようにする。`next-platform` はテストでは呼ばない。
- CI は `macos-latest` でビューのテストを走らせる。`core::Ui` のテストに GPU は要らない。

## Material 3 Expressive での再デザイン

デスクトップのプレーヤーとしての Hiphile の良さは残し、見た目を MD3E に移す。詰まったリスト、
メニューバー、コンテキストメニュー、大きさを変えられるペイン、コマンドのそばに出るショートカットは残す。
表現は再生を伝えるところに使い、ライブラリの長いところは詰めたままにする。

### トークン

### ガイド

代わりの 2 つのガイドを step 2 で書く。同じ step で AGENTS.md の最初の節を分け、`crates/` は gpui-kit の
ガイドに、`next/` は新しいガイドに従うと書く。

- **デザイン。** 上の決まりと、何にどの md3e の部品を使うかを、詰まったデスクトップアプリ向けに書く。今の
  ガイドのうち GPUI Kit に依らないところは残す：作業から始める、状態は見えるようにする、モバイルより
  デスクトップの約束を先にする、画面の言葉、アクセシビリティとレビューのチェックリスト。
- **コーディング。** コンポーネントの関数は一度だけ走る。変わるものはクロージャにする。シグナルは自分の
  スレッドから出さない。ビューは `next-host` を通してコアに従い、オーナーの中で呼ぶ。オーバーレイは
  `open` と `on_dismiss` を持つ子として置く。md3e の色は `dyn_style` の中で読む。md3e と prelude は名前
  （`button`、`switch`）が重なるので、名前を明示して import する。AppKit は `next-platform` からだけ
  触る。テストは上のとおり。

## フォークするなら

step 6 で決める。素のままで残る制限のうち、フォークすれば直せるもの：

| 項目 | 素のままでは |
| --- | --- |
| macOS の再描画の再帰を直す | ミニプレーヤーを戻すときは別のスレッドに開くので、シグナルを共有できない |
| ウィンドウの位置、最小サイズ、重なり、前に出すこと、フォーカスを取らないウィンドウを `WindowOptions` に | `next-platform` がタイトルで `NSWindow` を探していじっている。フォーカスを取らないミニプレーヤーは作れない |
| 信号機ボタンを残すモード | `next-platform` が見せ直している |
| テキストの省略記号と行数制限 | 切って右端を薄くしている |
| 点に出す md3e のメニュー | 大きさ 0 の要素に付けている |
| 外観のシグナル、動きを減らす設定 | `next-platform` が読んでいる。md3e の部品の動きは止まらない |
| macOS のロケールを読む、md3e のフォントの並び | `next-platform` が `LANG` を入れている |
| 差し替えられる時計 | テストでタイマーやばねを進められない |
| `performKeyEquivalent:` でキーマップが先にキーを見る | メニューにあるキーはアプリ全体のコマンドに限られる |
| 送り口のキューを捨てる | 橋渡しがオーナーの消えたあとに送らないようにしている |
| スタイルの setter が `f32` そのものを受け取る | Hiphile は `16.0_f32` と書いている。lint がハードエラーになると AntiWebUI がビルドできない |
| 波線のスライダーに流すかどうかと振幅を渡す口 | `slider_with` で自分の見た目を載せている |

フォークするなら、Hiphile はそのフォークをリビジョン固定で使い、上流に送るかは別に決める。

## リリースするなら

決めていない。リリースすると決めたら、次が要る。

- **更新の橋渡し。** updater は最新のリリースのバージョンだけを見て更新の有無を決め、自分のプラット
  フォームのアセットは入れるときにしか探さない（`crates/updater/src/install.rs:92-98`、`:145-155`）。
  そのまま切り替えると、次のことが起きる。
  - macOS 12・13 の GPUI 版が、そこで起動しないビルドを入れる。
  - Windows の GPUI 版が、入れられない更新を 6 時間ごとに見つける。
  - 橋渡しの版を入れていない古い版は、新しい名前のアセットを見つけられず、失敗し続ける。

  そこで判定を「`-macos{N}-{arch}.zip` のうち、N が今の macOS 以下で最大のものがあるときだけ更新あり」に
  し、GPUI 版にも AntiWebUI 版にも入れる。macOS のバージョンを読む口も要る。それより古い版のために、
  橋渡しの GPUI 版を旧名（`-macos-arm64.zip`、`-macos-x64.zip`、`-windows-x64.zip`）で添付し続ける。
  その場合、橋渡しの版自身は新しい名前だけを探すようにする。そうしないと自分を入れ直し続ける。
- **更新後の再起動。** 再起動の印を立てて `quit()` し、`main` が `run` と `shutdown()` を終えてから新しい
  バイナリを起動する。先に起動すると、保存と、デバイスのサンプルレートと hog の復元より先に新しい側が
  動く。今はタイトルバーにある「Restart to update」は、レールの設定のボタンのバッジと設定のポップアップに
  移す。
- **GPUI を消す。** GPUI のクレートと `gpui-host` を消し、`next/` を `crates/` に今の名前で移し、
  release-plz の設定、ガイド、AGENTS.md、`check-gpui-free`（どの UI フレームワークでも失敗するように）を
  直す。
- **同梱するもの。** Roboto Flex の OFL、Material Symbols の Apache ライセンスと NOTICE。
  `MACOSX_DEPLOYMENT_TARGET` と `LSMinimumSystemVersion` を 14 にする。
- **取り残される利用者。** macOS 12・13 と Windows は、GPUI 版の最後のリリースに留まる。

## 決まったこと

2026-11-12：

1. **まずはフォークしない。** 上流の AntiWebUI をリビジョン固定の git 依存で使い、素のままでできる範囲を
   作る。足りないものは Hiphile の側でしのぐか、制限として残す。フォークするか、上流に変更を送るかは、
   比べたあとで決める。このアカウントはリポジトリに push できない。
2. **ウィンドウの上端は中身と一体のまま、信号機ボタン付き。** タイトルバーの帯は置かず、ボタンはレールの
   上端に重なる。素のままでは `next-platform` がクライアント側の装飾のウィンドウにボタンを見せ直す。
   できなければ、標準のタイトルバーで進める。
3. **最小は macOS 14。** そこからはフレームの間隔の調整が正しく動く。
4. **はじめは macOS だけ。** Windows のために GPUI を残すことはしない。
5. **配色は既定でカバーから作る。** 固定の種の色も選べる。
6. **スクリーンリーダーは無くてよい。**
7. **この移行は試し。** どんな感じかを見るためで、リリースと切り替えは決めていない。
8. **今のキーマップは仮。** そのまま移さず、新しく決める。
9. **ミニプレーヤーは後回し。** ウィンドウはメインの 1 つだけで始める。
10. **設定は同じウィンドウのポップアップで作り直す。** 別のウィンドウにはしない。
11. **タイトルバーのタブはナビゲーションレールで作り直す。** タイトルバーにあったほかのもの（戻ると進む、
    サーバー、設定）も、レールとアプリバーに移す。

## リスク

- **成熟度。** AntiWebUI は主に作者 1 人の 10 日分の仕事で（git の作者名は bea4dev が 68 件、
  masahiro_abe が 2 件）、CI が無く、多くは合成イベントでしか確かめられていない。macOS でのライブリサイズ、
  日本語の入力、トラックパッド、⌘Q、全画面は手で確かめられていない（d38:339-345）。リビジョンを固定し、
  更新は意図して行う。
- **AppKit を外から触ること。** `next-platform` は AntiWebUI が持つ `NSWindow` とメインメニューを横から
  変える。AntiWebUI がそれを戻したり、前提が食い違ったりしうる。固定したリビジョンを上げるたびに確かめる。
- **範囲。** ネイティブのメニュー、シート、ネイティブのコントロールは AntiWebUI がやらないと決めている。
- **将来の rustc。** `float_literal_f32_fallback` がハードエラーになると、上流がスタイルの setter を
  変えるまで AntiWebUI がビルドできない。フォークしないなら待つしかない。
- **Intel。** AntiWebUI では試されていない。
- **デスクトップでの MD3E。** md3e の部品はタッチ向けの大きさ。詰まったリスト、表、設定には Hiphile の
  寸法が要り、デザインのガイドがそれを守らせる。
- **テスト。** 260 のビューのテストは移すのではなく書き直しになり、タイマーやばねは進められない。
- **大きさ。** Roboto Flex で約 1.8 MB、アイコン 1 つで約 3 KB 増える。SVG の文字を有効にすると 1.6 MB。
- **2 つのアプリを同時に持つこと。** step 2 から 6 の間に GPUI のビューを直すと、二度直すことになる。
  直すのはバグだけにする。

## 試しの終わりの条件

- `hiphile-next` で、macOS 14 で[比べる項目](#比べる項目)をすべて確かめられる。
- コアのクレートが gpui-kit に依存していない（step 1）。
- CI がフォーマット、`-D warnings` の clippy、ビューのテストを含むテスト、チェックを走らせる。
- step 0 の結果、素のままで残った制限、使ってみて分かったことがここに書いてあり、続けるか、フォークするかが
  決まっている。

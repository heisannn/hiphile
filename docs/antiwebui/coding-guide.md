# コーディングのガイド

`next/` のコードを書くとき、レビューするときに読む。AntiWebUI と `anti-webui-md3e`（以下 md3e）の上で、
コアに従うビューをどう組むかを書く。先に[デザインのガイド](design-guide.md)を読む。コードの作りは
デザインの意図を保つためのもので、置き換えるものではない。何を作るかは[UI を AntiWebUI に移す](migration.md)が
決める。`crates/` の GPUI 版は今までどおり gpui-kit のガイドに従う。AGENTS.md のコメント、自明な文言、
ビューを小さく保つ、コミットの前に、の節は `next/` にもそのまま当てはまる。

「しなければならない」は寿命、正しさ、約束のための制約で、「する」は既定、外れるには具体的な理由が要る。
正確なシグネチャは今のソースが正しい。AntiWebUI はリビジョン `25e82a1` のソースと `docs/design/`、md3e は
その `src/anti-webui-md3e` を読む。

## 構成

| クレート | 持つもの |
| --- | --- |
| `next-host` | コアに従うこと：`install`、`executor`、`follow`、`notices`、`on_ui`、`Scope`、`Pending`。これからカバーの取得と共有 |
| `next-platform` | AppKit を直接呼ぶもの（メニューバー、メインウィンドウ、外観、動きを減らす設定、`LANG`）。これから作る |
| `next-ui` | テーマ、文字、ウィンドウを動かす上端、`Screen` と `app_bar`、`Command` と `Commands`、テストの道具。これからキーマップ、`row_list`、共通の部品 |
| `next-account` ほか画面のクレート | 1 つの画面、パネル、ポップアップずつ |
| `next-hiphile`（バイナリ `hiphile-next`） | 起動、シェル、ルーティング、メニューバーのコマンド |

- 依存は下を向く。画面のクレートは `next-ui` と `next-host` とコアに依存してよいが、シェルや隣の画面の
  中身に依存してはならない。
- 画面は機能ごとのクレートに置き、そのモデル、ビュー、コマンド、ダイアログを一緒に持つ。全体の `views/` や
  `dialogs/` に分けない。
- シェルは画面を組み合わせ、機能のロジックはほとんど持たない。画面がシェルに頼むことは `next_ui::Command` に
  し、渡された `Commands` で送る（`commands.send(Command::OpenSettings)`）。
- 2 つ目の画面が同じ UI を要るようになったら `next/ui` に移す。1 つの画面のためだけに `next-ui` に置かない。
- クレートは、状態と寿命を持つか、安定した境目があるか、別にビルドしテストする意味がある大きさのときに
  分ける。画面やヘルパーごとに作らない。
- `next-*` は `hiphile-core` の下に入れない。コアはモバイルからも使うので、デスクトップの UI に依存させない。

## リアクティブの基本

AntiWebUI のシグナルはスレッドローカルで、細かく更新される（d02）。

- **部品の関数は一度だけ走る。** そこで作るのはシグナル、子、ハンドラ、コアへの橋渡し。変わるものは
  クロージャにし、そのクロージャが読んだシグナルが変わったときに走り直す。部品の関数の中で `get()` した
  値は、そのとき一度きりの値で、あとから変わらない。
- **見た目の変わるものは `dyn_style` に入れる。** md3e の色は `color_scheme()` を `dyn_style` の中で読む。
  部品の関数の中で読むと、配色が変わっても（カバーからのクロスフェードも）その色のまま残る。

  ```rust
  div().dyn_style(|s| s.bg(color_scheme().surface_container))
  ```

- **中身が入れ替わるところは `dyn_view`、`show`、`for_each`。** `dyn_view` の中で部品を組み立てるときは
  `untrack` で包まなければならない。包まないと、組み立ての途中で読んだシグナルを `dyn_view` が追い、関係の
  ない変化で全体を作り直す。

  ```rust
  dyn_view(move || match workspace.get() {
      None => untrack(|| signed_out(hiphile.clone())),
      Some(workspace) => untrack(|| signed_in(hiphile.clone(), workspace, shown, snackbars)),
  })
  ```

- **作り直したくない値は `memo` で切る。** 大きなスナップショットのうち要るところだけを `memo` にし、
  それを読む。シェルはスナップショットの中のワークスペースだけを `memo` にしていて、サインイン中の変化で
  サインインの画面が作り直されない。`memo` は値が変わったときだけ知らせるので、値は `PartialEq` にする。
- **シグナルの読み方。** 追うときは `get` と `with`、追わずに今の値だけ要るとき（ハンドラの中など）は
  `get_untracked`。変えるときは `set` と `update`。
- **小さな状態のまとまりは `Copy` なハンドルにする。** シグナルは ID なので、いくつかのシグナルを持つ
  struct は `Copy` にでき、クロージャにそのまま渡せる（`Navigation`）。
- **`effect` は副作用だけ。** 読んだシグナルに合わせて外のものを動かす（コアに今の移動先を伝える、配色を
  設定する）。シグナルからシグナルを作るのは `memo` にする。
- **`effect` の中で、その `effect` が読むシグナルを書かない。** `memo` を通して読んでいても同じ。
  AntiWebUI はその書き込みによる走り直しを落とし、`memo` は古い値のまま残る。書く先は `untrack` で読むか、
  書くのをハンドラに移す。

## スレッドと状態

### コアの動くところ

- コアは `main` が作るマルチスレッドの tokio のランタイムで動き、`Executor::tokio` として渡される。
- `App::run` が戻ったら、`Hiphile::shutdown()`、ランタイムの `shutdown_timeout`、最後の `net::Client` の順に
  落とす。`shutdown_timeout` にするのは、ライブラリの同期がブロッキングのスレッドで `block_on` していて、
  普通に落とすとその終わりを待つため。最後の `net::Client` は tokio のランタイムの中で落としてはならない。
- **シグナルは自分のスレッドから出さない。** `Signal<T>` は ID だけなので `Send` になってしまうが、
  ランタイムの無いスレッドで使うとパニックし、別の UI スレッドでは同じ ID が別の値を指しうる。UI スレッドの
  外のコードはシグナルではなく `UiSender` を持つ。

### コアに従う

コアに従うのは `next-host` を通す。ビューはコアのハンドルに従い、ビューの状態だけを持つ。

- UI スレッドごとに、ビューを作る前に `next_host::install(executor)` を一度呼ぶ。`next_host::executor()` は
  その executor を返す。
- `follow(watch::Receiver<T>) -> Signal<T>`：スナップショットの `watch` をシグナルにする。UI スレッドに
  送るのは「変わった」という知らせだけで、UI スレッドで最新の値を読む。続けて出た変更は最後の 1 つに
  まとまり、古い値に戻ることも、UI が止まっている間にキューが伸びることもない。
- `notices(broadcast::Receiver<T>, f)`：通知ごとに UI スレッドで `f` を呼ぶ。遅れすぎて取りこぼした古い
  通知は飛ばす。チャンネルどうしの順序は送った順ではなく作った順になるので、通知のハンドラで状態が要る
  ときは `follow` のシグナルではなくコアの `snapshot()` を読む。
- `on_ui(task, f) -> Pending`：コアの `Task<R>` を待ち、オーナーが残っていれば UI スレッドで `f` を呼ぶ。
  オーナーが消えると `f` は呼ばれず、タスクも取り消される。`Pending::cancel` で取り消せ、`is_waiting` で
  待っているかを読める。`Pending` を落としても待ち続ける。
- **どれもオーナーの中（部品の関数の中など）で呼ばなければならない。** オーナーの外では `on_cleanup` が
  渡したものをその場で捨てるので、タスクがすぐ止まり、黙って従わなくなる。デバッグビルドでは panic する。
- **イベントのハンドラ（`on_click` など）はオーナーの外で走る。** ハンドラからコアの `Task` を待つときは、
  部品の関数の中で `Scope` を取り、ハンドラでその `on_ui` を呼ぶ。オーナーが消えたあとの `scope.on_ui` は
  タスクをすぐ取り消す。

  ```rust
  let scope = next_host::Scope::here();
  let submit = move || {
      if let Ok(task) = hiphile.sign_in(&server.get_untracked(), &username.get_untracked(), &password.get_untracked()) {
          *attempt.borrow_mut() = Some(scope.on_ui(task, finish));
      }
  };
  ```

- **`watch` の値は、借用を持ったままシグナルに入れない。** 先に写してから入れる。

  ```rust
  let now = rx.borrow().clone();
  value.set(now);
  ```

  `value.set(rx.borrow().clone())` は文の終わりまで借用が残る。`set` が走らせたビューがコアを呼ぶと、
  コアが同じロックで publish しようとして止まりうる。
- 呼び出しの結果をすぐ見せるビューは、呼んだ直後にコアの `snapshot()` を読む。
- 再生位置は出されない。プレーヤーバーは 250 ms ごと、歌詞は 50 ms ごとに `position()` を読み、見えている
  間だけ `set_timeout` をかけ直す。一定間隔のタイマーは置かない。

### 状態の持ち主

それぞれの状態は、正しく保てる一番狭い持ち主に置く。

- 領域の状態（ライブラリ、再生、設定、サインイン）はコアのもの。ビューはそれを `follow` で写すだけで、
  別の正しい値を持たない。
- ビューの一時の状態（開いているか、入力中の文字、選んだ行）は、それを描く部品のシグナル。
- 画面をまたぐ状態（今の移動先と履歴、設定のポップアップが開いているか）はシェルが持ち、画面には
  `Commands` か `Copy` なハンドルで渡す。
- コアのスナップショットの写しを画面ごとに持たない。シェルが一度だけ `follow` し、シグナルを渡す。

値は制御して渡す：今の値を部品に渡し、変えたいという要求を受け、持ち主を変える。md3e の多くの部品は状態を
値を読むクロージャで受け、変更はアプリがする（`.selected_when(...)`、`.disabled_when(...)`、
`expanded_when(...)`）。スイッチ、スライダー、テキストフィールドのように `Binding`（`Signal`）を受けて部品が
変えるものもある。どちらでも、持ち主は 1 つにする。

### 状態のループを避ける

テキスト、選択、絞り込み、制御されたポップアップには 2 つの道がある：持ち主が値を変える道と、利用者の操作が
新しい値を求める道。持ち主が入れた値を、利用者の操作として送り返さない。どちらから来たかを持つか、
まとまったスナップショットを比べ、1 つの変化を一度だけ知らせる。ハンドラがその場で部品を閉じたり替えたり
しても壊れないようにする。

`effect_with` で「最初の一回」と「そのあとの変化」を分けてよい（サインインは、最初の実行のあとの入力で
再サインインを取り消す）。

## 安定した識別

- `for_each` のキーはものの安定した ID にする（曲、アルバム、プレイリストの ID、移動先の位置）。並べ替えの
  できるリストの位置や、訳したラベルをキーにしない。
- キーが変わるのは、UI としての同一性が変わること。リセットは意図して起こす。
- `node_ref` は部品の関数で作って持ち、`dyn_view` の中で作り直さない。

## スタイル

- 色、角、余白、部品の大きさを決め打ちしない。色は `color_scheme()` の役割から取り、役割が足りなければ
  `next_ui::theme` に足す。色のリテラルを書くのは `next_ui::theme` だけ。
- 文字は md3e の `TextStyle` から取る。`next_ui::type_scale` の `body`、`styled_text`、`muted_text`、
  `error_text` が、段階と配色の色を一緒に当てる。
- **スタイルの setter で小数は `16.0_f32` と書く。** setter は `impl Into<f32>` を受けるので、`.p(16.0)` の
  リテラルは型が決まらず、`float_literal_f32_fallback` で `-D warnings` の clippy に落ちる。長さ（`w`、`h`、
  `m*`、`inset`、`top` など）は整数も受けるので、`.h(64)`、`.mr(16)` と書いてよい。
- 繰り返す寸法は名前の付いた定数にし、同じ関係は同じ定数から取る。1 px のずれを px の補正で直さず、
  重なった余白、入れ子の内側の余白、境目の持ち主のどれが違うかを探して直す。
- 状態に依らない形は普通のつなぎに書き、状態で変わるものだけを `dyn_style` に入れる。
- 押す、ホバー、フォーカスの見た目は md3e の部品の状態レイヤーに任せる。自分で作った `div` に同じ見た目が
  要るときは `Ink` を使う。
- 外向きのフォーカスの輪は場所が要る。`overflow_hidden` の親は輪を切る。切るときは、キーのフォーカスが
  見えなくならないようにする。
- 横に並べた列がその行の高さいっぱいに伸びるかを確かめる。伸びてスクロールする子には `flex_1` と
  `min_w(0)` か `min_h(0)` を付け、縮めるのはどの子かをはっきりさせる。
- スクロールは 1 つの面が持つ。スクロールバーが面の端に付くよう、余白はスクロールする面の内側に置く。

## md3e の部品を使う

- **md3e のものは名前を明示して import する。** md3e と AntiWebUI の prelude は名前（`button`、`menu`、
  `switch`、`dialog` など）が重なる。prelude は glob で入れ、md3e は名前を挙げる。明示の import が glob に
  勝つ。

  ```rust
  use anti_webui::prelude::*;
  use anti_webui_md3e::color_scheme;
  use anti_webui_md3e::components::{IconButtonStyle, styled_icon_button};
  use anti_webui_md3e::icons;
  ```

- `next_host::follow` と prelude の `follow`（目標が変わったときにばねを始める値）も重なる。コアに従うファイル
  では `use next_host::follow;` を明示する。両方が要るファイルでは片方をパスで呼ぶ。
- **アイコンだけのボタンには名前を付ける。** `.access(|a| a.label("Back"))`。`access` は重ねられるので、
  部品が付けた役割に名前を足せる。状態で変わる名前はクロージャの中で読む（レールの開け閉めのボタン）。
- **中身から取った名前には、アイコンの字形が頭に入る。** md3e の部品が中身から名前を取ると、私用領域の
  文字が名前の頭に入る（レールの項目は `"\u{e9b2} Home"`）。`next_ui::testing::find` と `press` はそれを
  除いて比べる。名前がはっきり要るものには `.access` で付ける。
- **画面の見出しは `next_ui::app_bar`。** md3e の `TopAppBar` はナビゲーションのボタンを 1 つと決め打ちして
  いて（見出しが 60 px の位置）、戻ると進むを並べられない。画面は `next_ui::Screen { title, actions, body }`
  を返し、シェルがそれを `app_bar` とペインに置く。`TopAppBar` は戻るボタンの要らないところ（設定の
  ポップアップの中）では使ってよい。
- **オーバーレイは `open` と `on_dismiss` を持つ子として置く。** メニュー、ダイアログ、ポップアップは、
  開いているかを読むクロージャと閉じるクロージャを受け、部品の子として宣言する。描くのは `portal` か
  ポップアップの中だが、論理的には宣言した場所の子で、そのオーナーと一緒に消える。

  ```rust
  styled_menu(move || open.get(), move || open.set(false), groups, MenuStyle::new().anchor(anchor))
  ```

  開いているかのシグナルは、出したボタンが持つ部品が持つ。ボタンはそれを読んで、開いている間は押された
  見た目にする。
- **md3e のメニューの項目の名前には、後ろに出るキーも入る。** 「Remove」の項目の名前は `"Remove ⌫"`、
  「Go to Artist」は `"Go to Artist ⇧⌘A"`。テストではキーまで含めて探す。
- md3e の `search_bar` は、開くと別のポップアップのウィンドウではなく、同じウィンドウの中のモーダル
  （`portal`）になる。
- **md3e の部品は普通の `Div` を返す。** `.w(...)`、`.on_click(...)` を続けてよい。見た目だけを変えたいときは
  `*_with`（`slider_with` など）で標準の振る舞いに載せ、似た部品を `div` で作り直さない。
- スナックバーは `snackbars()` をシェルで一度作り、`Snackbars` を渡す。1 つずつ順に出て、アクションのある
  ものは閉じるまで残るので、元に戻すものには `lasting` で時間を付ける。

## ウィンドウとプラットフォーム

- ウィンドウにタイトルバーの帯は無い。上端は `next_ui::window::moves_window` で包み、ドラッグでウィンドウを
  動かし、ダブルクリックで拡大させる。その中の押せるものは `kept_still`（`on_pointer_down` で
  `stop_propagation`）で包む。包まないと、押したときにウィンドウが動き出す。
- AppKit は `next-platform` からだけ触る。メインスレッドでだけ呼ぶ。`unsafe_code` はそのクレートの
  モジュールでだけ許し、それぞれに理由を書く。テストでは呼ばない。
- macOS で 1 つのスレッドにウィンドウを 2 つ開かない（再描画が再帰しうる）。2 つ目のウィンドウは
  `spawn_window` で専用のスレッドに開き、シグナルを共有しない。
- 画面はウィンドウの大きさを `on_resized` で受け、`memo` で段に分ける（レールは 1000 px より狭いと畳む）。

## イベントとキーとフォーカス

- 1 つのコマンドは一度だけ書く。ボタン、メニューの項目、コンテキストメニュー、メニューバー、キーは同じ
  `Command` を送るか、同じ持ち主の関数を呼ぶ。ラベル、アイコン、キー、有効かどうかは 1 つの決まりから
  取る。コマンドの有効と無効は `memo` で決まり、メニューバーも同じ `memo` を読む。
- キーの経路は 2 つ。メニューバーにあるキーはアプリ全体のコマンドとしてメニューが受ける。それ以外は
  `next-ui` のキーマップが `key_context` の付いた要素で受け、内側のコンテキストが勝つ。使ったキーには
  `stop_propagation` と `prevent_default` の両方をかける。フォーカスがテキストの入力欄にあるときは、文字に
  なるキーを入力欄に譲る。
- `stop_propagation` は、入れ子の操作が親に同じイベントを渡してはならないときだけ使う（`kept_still` のように）。
  何にでもかけると、メニュー、選択、ドラッグ、ウィンドウのコマンドが分かりにくく壊れる。
- フォーカスの持ち主をはっきりさせる：キー操作を持つ要素を `focusable` にし、オーバーレイを開いたら
  フォーカスを移し、閉じたら戻す。フォーカスが無いとキーはルートにしか来ないので、失ったときに戻す。
- 部品をまとめて作るとき（リスト、メニュー）は、矢印での移動、Home と End、決定、取り消し、Tab まで、
  移動の型をひととおり作る。
- 押せるものを作るときは、まず md3e の部品を使う。自分の `div` を押せるようにするときは、`focusable`、
  役割、名前を揃える（`server_menu` のアバターのボタン）。`focusable` な要素では Space と Enter が
  クリックになる。

## 非同期の仕事

- 仕事はイベント、部品の関数、名前の付いた関数から始め、走り直すクロージャ（`dyn_style`、`dyn_view` の
  中身、`memo`）の副作用として始めない。
- 非同期の操作は、待っていない、待っている、できた、失敗した、をはっきり状態で持つ。待っている間も前の
  データを見せられるなら見せる。取り返しのつかない操作を二度送らせない。直せるエラーは画面に出し、ログを
  利用者へのフィードバックにしない。
- 結果は、頼んだあとで画面、選択、サインインが変わってから届きうる。古い結果は `Pending::cancel` で
  取り消すか、何に対する結果かを持って捨てる。
- 重い計算（カバーから種の色を探すなど）はコアの executor のタスクで行い、結果を `on_ui` で受ける。

## 長いリスト

- 大きくなりうるものは見えている行だけを作る（`virtual_list` の上の `next_ui::row_list`）。
- 次のものを分けて持つ：元のデータと ID、並べ替えと絞り込み、選択、スクロール、行の描き方。
- 選択は ID で持ち、並べ替えと絞り込みをまたいで保つ。キーでの選択と、その行までのスクロールは、ほとんどの
  行が今のフレームに無くても、データの位置で動かす。
- `NodeRef::logical_rect()` はレイアウトの前は 0×0 か `None`。キー以外で選んだ行までのスクロールは
  `row_list::scroll_to_row` で行う。リストがまだ並んでいなければ何もせず `false` を返すので、`on_resized`
  で受けてやり直す。
- 選択は `next_ui::selection::selection_fill` の塗りで示し、行の文字の色は選んでも変えない。
- 行を描く関数は副作用を持たない。いつ走ってもよいようにし、仕事を始めたり、データを足したり、限りなく
  購読を増やしたりしない。

## 公開 API

再び使う部品では：

- 作る関数は正しい既定の値を持つ
- ビルダーは `Self` を受けて返し、領域の言葉を使う
- コールバックは求められた変化を言い、ポインタの詳しさが要るときだけポインタのイベントを渡す
- 振る舞いを持ち、変わっていく型はフィールドを非公開にし、作るのはビルダー、読むのは読み出しにする
- 公開のフィールドは、記録のような設定、トークン、形、保存する形に使う（`Screen` のように）。フィールドを
  公開する struct には、作る関数か `Default` かビルダーも用意する
- 子を探って中身を見つけず、名前の付いた部分を受ける
- 再び使う振る舞いを足すときに、製品の見た目を押し付けない

モジュールの公開の道は、中を組み替えても変えない。`lib.rs` で意図して再公開する。

## 名前

- ビューと状態は製品の概念で名付ける：`sign_in`、`rail`、`server_menu`、`settings_popup`、`Navigation`。
- 部品の関数は、それが見せるものの名詞にする。ハンドラは意図で名付ける（`submit`、`switch`、`finish`）。
- 1 つのモジュールには 1 つの主な役目。状態の持ち主や寿命が、関係のない振る舞いを読まないと分からなく
  なったら分ける。
- 同じ概念には部品をまたいで同じ言葉を使う。新しい名前の前に AntiWebUI、md3e、`next/` で決まった言葉を
  探し、無ければ macOS の部品の言葉を使う。

| 概念 | 形 | 例 |
| --- | --- | --- |
| 部品を作る関数 | 名詞 | `sign_in`、`rail`、`app_bar` |
| 部品が見せる値 | 名詞 | `Screen` |
| 共有するハンドル | 役割の名詞 | `Navigation`、`Commands`、`Scope` |
| 頼みごと | 動詞か意図の名詞 | `Command::GoBack`、`Command::OpenSettings` |
| 作る | `new` か意味のある名前 | `Screen::new`、`Scope::here` |
| 流れるように足す | 名詞、形容詞 | `action`、`label`、`placement` |
| その場で変える | `set_<field>` | `set_items` |
| 真偽を読む | `is_<形容詞>`、`has_<名詞>` | `is_waiting`、`is_dark` |
| 値を読む | フィールドの名詞 | `destination` |
| コールバックを登録する | `on_<イベントか意図>` | `on_click`、`on_dismiss`、`on_submit` |

- 新しい真偽の読み出しに `can_` を使わない（`can_go_back` は GPUI 版から来た名前）。
- 囲むものが文脈を持つ。フィールドは型の中で、引数は関数の中で読まれるので、囲むものを繰り返さない。
- 言葉を正確に使う：**selected** はずっと残る選択、**focused** は今のキーの的、**hovered** はポインタが
  乗っていること。**open/close** はオーバーレイ、**show/hide** は一時の見せ方、**expand/collapse** は構造。
  **disabled** は操作できない、**readonly** は見て選べるが変えられない、**loading** は待っている間の二度押しを
  防ぐ。**index** は今の位置、**id** は安定した同一性で、並べ替えのできるものを位置で持たない。
- `data`、`handle_action`、`update_ui`、`process`、`manager` のような曖昧な名前を避ける。
- Rust の型は `UpperCamelCase`、モジュール、関数、フィールド、変数は `snake_case`、定数は
  `SCREAMING_SNAKE_CASE`。0 始まりの位置は `ix`、ID は `Id` を付ける。
- `rustfmt` に従い、ワークスペースの clippy を通す。関係のない警告まで隠す広い `allow` を置かない。

## テスト

### どの層で確かめるか

振る舞いを証明できる一番低い層で確かめる：

1. 純粋なテスト：状態の移り、順序、形（`Navigation` の履歴はコアの `History` で確かめられる）
2. `next-host` のテスト：`follow`、`notices`、`on_ui` が UI スレッドに届き、オーナーと一緒に止まること
3. `core::Ui` に載せたビューのテスト：合成イベントを送り、アクセシビリティの木で役割と名前で探す
4. 画面の絵：`shots` の例

押せる部品では、仕組みではなく意味の約束を確かめる：ポインタとキーでの操作、制御された値の変化、無効の
振る舞い、フォーカスの移り、知らせの数と順、安定した同一性、大事な空と失敗の状態。決まって再現できる
バグは、直す前にテストを足す。

### ビューのテスト

- ビューのテストは `<view>/tests.rs` に置く。
- `next_ui::testing`（`test-support` の機能）がウィンドウなしで動かす。GPU は要らない。
  - `start(view)`、`start_at(view, (w, h))`：フォーカスのあるウィンドウに出す。既定の大きさは `WINDOW`
  - `press(ui, role, label)`：アクセシビリティの操作として押す。ポップアップの中にも届く。無効なら失敗する
  - `find(role, label)`、`nodes(role)`、`has_text(text)`：見えているものを探す
  - `focus(ui, role, label)`、`typed(ui, text)`、`key(ui, named)`、`key_with(ui, key, modifiers)`：キーの入力
  - `click(ui, x, y)`、`click_text(ui, text)`、`middle_of(text)`：座標での入力。木で届かないときだけ使う
  - `frames(ui, ms)`：アニメーションのフレームを進める
  - `wait_until(ui, done)`：UI スレッドに届いたものを取り込み、レイアウトし、`done` になるまで待つ
  - `core(config)`：その設定ファイルを持つ、専用のフォルダのコアを作り、この UI スレッドに `install` する。
    設定には `romaji_search = false` が足される
  - `signed_in_core(server)`：ビューから見てサインインしたコア。ユーザーのライブラリの場所には何も書かない
  - `NOWHERE`：届かないサーバー
- コアはテストごとの tokio のランタイムで動く。`core` と `signed_in_core` が返す `TestCore` は最後まで
  持たなければならない（`let (_core, hiphile) = core("");`）。`_` に捨てると、すぐにランタイムが落ちる。
- 最後の `net::Client` は tokio のランタイムの中で落としてはならない。テストの偽のサーバーへのセッションも
  自分のクライアントを持つので、`TestCore` がそれを預かり、落とさずに残す。ランタイムを止めると、その
  スレッドがコアを持つタスクを落とし、そこで最後のクライアントが落ちうるため。新しい道具でクライアントを
  作るときも `TestCore` に預ける。
- スケール 2 では、アクセシビリティの木の位置からスクロールの半分しか引かれない。スクロールした中身の位置を
  木の `bounds` で確かめない。
- 設定は一時のストアを使い、`Store::user()` を使わない。本当にサインインを成功させるとユーザーの場所に
  カタログを開きうるので、サインインのテストは失敗の道で確かめ、サインインしたあとの画面は
  `signed_in_core` で作る。
- 名前で探せるように、確かめたいものには役割と名前を付ける。木は操作のたびに読み直す。前の
  `AccessNode` は古い写し。
- タイマーとばねは進められない（`set_timeout` と `animated` は `Instant::now()` を読む）。時間ではなく状態を
  確かめる。閉じる動きの終わりを待つときは `frames` で十分なフレームを進める。
- 今はコアの仕事が別のスレッドから届くので、`wait_until` で待つ。並行してテスト用の決定的な executor を
  作っていて、それが入ったら、park するまで回して UI スレッドに流す道具に置き換わる。
- テストのコアはメディアコントロールにつながない。`next-platform` はテストで呼ばない。
- 自動の確かめと、手で確かめたことは分けて書く。

### 画面の絵

`cargo run -p next-hiphile --example shots -- <folder>` は、ウィンドウを開かずに画面を PNG に描く。GPU は
使う。ライトとダークの両方を描く。絵はアクセシビリティの木で言えない見た目を確かめるためのもので、
キー操作やフォーカスの代わりにはならない。

## 性能

- 走り直すクロージャの中で状態を変えない。
- シグナル、子、ハンドラ、橋渡し、重いデータを、走り直すたびに作らない。
- 大きなスナップショットを読むのは `memo` で要るところだけにする。
- 長いものは見えている行だけを作る。
- クロージャのためだけに大きな文字列やコレクションを写さない。`Rc` やハンドルを渡す。
- キャッシュは測ってから足し、無効にする持ち主をはっきりさせる。
- アニメーションの仕事は限りがあるようにし、動きを減らす設定に従う。
- `wght` のように文字幅を変える軸を動かすと、毎フレーム整形とレイアウトが走る。

## よくある失敗

- 部品の関数で `get()` した値を、変わるものとして使う
- `color_scheme()` を `dyn_style` の外で読み、配色が変わっても色が残る
- `dyn_view` の中を `untrack` で包まず、関係のない変化で作り直す
- ハンドラの中で `on_ui`、`follow`、`notices` を呼び、黙って何も起きない
- `watch` の借用を持ったまま `set` し、コアと止まり合う
- `.p(16.0)` と書き、CI の clippy に落ちる
- md3e の名前を glob で入れ、prelude の同じ名前とぶつかる
- アイコンだけのボタンに名前が無く、テストで探せない
- `moves_window` の中の押せるものを `kept_still` で包まず、押すとウィンドウが動く
- テストで `TestCore` を `_` に捨てる
- `effect` の中で、その `effect` が読むシグナルを書き、走り直しが落ちる
- レイアウトの前に `logical_rect()` を読み、0×0 の位置でスクロールする
- 1 つの部品にアプリ全体の関係のない状態を持たせる
- ビューの中にコアの状態の写しを持ち、ずれていく
- 位置や訳したラベルを `for_each` のキーにする
- 色のリテラルを画面に書く
- 押せる `div` を作り、md3e の部品が持つフォーカス、キー、無効、名前を失う
- 取り返しのつく軽い操作に確認のダイアログを出す
- 中の関数を呼ぶだけで、キーとポインタを通さないテスト

## コーディングエージェントへ

書く前に、いちばん近い実装、そのテスト、再公開の境目、使う部品のソースと `docs/design/` を読む。React、
CSS、GPUI の例からの類推で書かず、今のソースでシグネチャを探す。

変更ごとに、次を言えるようにする：

1. 振る舞いの持ち主と見た目の持ち主
2. 同一性と状態の寿命、どのオーナーの中で何を呼ぶか
3. ポインタ、キー、フォーカス、アクセシビリティの約束
4. レイアウトとはみ出しの持ち主
5. 使うトークンと、意図した例外
6. 振る舞いが壊れたら落ちるテスト

コンパイルが通ることは UI の質の基準ではない。生成したコードを見た目だけ整える大きな書き換えは、
リポジトリの作りに合わせることの代わりにならない。アプリは確かめる手順に入っているときだけ起動する。

## 確かめること

レビューに出す前に：

- 状態と副作用の持ち主がはっきりしている
- コアに従うものはすべてオーナーの中で作られ、ハンドラからの待ちは `Scope` を通る
- 変わるものはクロージャか `dyn_style` か `dyn_view` に入っていて、`dyn_view` の中は `untrack` で包んである
- 繰り返すものは ID をキーにしている
- 色、文字、形はトークンから来ていて、例外には理由がある
- md3e の名前は明示して import している
- キー、フォーカス、無効、オーバーレイが一緒に動く
- 読み込み、空、エラー、取り消しの道がある
- 長いものは見えている行だけを作る
- 公開 API が依存の向きと隠すべきものを守る
- 振る舞いを適切な層のテストが証明している
- AGENTS.md の「Before committing」のチェックが通る
